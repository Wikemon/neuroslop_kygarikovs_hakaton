# Как писать код в проекте хакатона

Мы читаем ноутбуки сверху вниз. По ячейкам должно быть видно, откуда взялись данные, как получился признак и что изменилось после обработки.

## Что уже характерно для проекта

| Где | Что сохраняем в новых правках |
| --- | --- |
| `data_clearing.ipynb` | Понятные pandas-маски, обработка по таблицам, проверка размеров и просмотр нескольких строк. |
| `feature_engineering.ipynb` | Разделы по источникам данных, признаки с отдельными именами, агрегации и объединения по `listing_id`. |
| `model.ipynb` | Отдельные блоки загрузки, подготовки, оценки и сохранения. Предобработка внутри `Pipeline`. |
| `sentence_transformers.ipynb` | Отдельные шаги загрузки сообщений, оценки текста, агрегации по чатам и сохранения признаков. |

## Как строить ноутбук

1. **Один смысловой шаг на ячейку.** Объявить маску и применить её можно вместе. Загрузку таблиц, расчёт признака и сравнение моделей удобнее держать в разных ячейках.
2. **Короткие заголовки и пояснения на русском.** Заголовок называет действие, например «Активность переписки перед закрытием». Комментарий объясняет решение, которое трудно понять из кода, например откуда взялся порог или почему пропуск сохраняется.
3. **Показывать результат в том же разделе.** `print()` подходит для числа строк и кратких итогов, `display()` или последнее выражение ячейки — для `.head()`, таблицы распределений или метрик.
4. **Расположить зависимости сверху.** Пути и настройки запуска держать в начале ноутбука. Для файлов проекта использовать пути от корня репозитория. Каждая переменная должна появляться раньше ячейки, которая её читает.

## Как писать pandas-код

- Имена в `snake_case` и на английском, как имена колонок. `features`, `messages_clean`, `bad_time` и `blocked_ids` помогают понять, что содержится в переменной. Короткое `df` читается, если в текущем блоке только одна таблица. В модели естественны `X_train` и `y_train`.
- Если условие длинное или понадобится для проверки, дать ему имя. Изменять значения по условию через `.loc`. Для длинных выражений использовать скобки и переносы, как в соседних ячейках.
- Сначала назвать результат агрегации, затем присоединить его. В `merge()` явно указывать ключ и тип соединения. Когда важна одна строка на объявление, указывать `validate="one_to_one"` и проверять число строк после объединения.
- Различать ноль и пропуск. Ноль уместен для счётчика, когда отсутствие записей действительно означает отсутствие действий. Неизвестную цену или длительность оставлять пропуском. Подстановку медианы для модели держать в обучаемом `Pipeline`.
- Форматирование брать из соседнего блока. Для новых строк подходят четыре пробела, двойные кавычки и пустая строка между смысловыми шагами. Переоформлять весь ноутбук ради небольшой правки смысла нет.

Пример в стиле очистки проекта. Порог применяется к обеим ценам, а число затронутых объявлений остаётся видно после запуска.

```python
price_columns = ["price", "current_price"]
high_prices = (listings[price_columns] > 20_000_000).any(axis=1)
low_prices = (listings[price_columns] < 20).any(axis=1)
bad_prices = high_prices | low_prices

listings.loc[bad_prices, price_columns] = float("nan")

print("Объявлений с аномальной ценой:", bad_prices.sum())
display(listings.loc[bad_prices, ["listing_id", *price_columns]].head())
```

## Проверки и функции

- В ноутбуке важные условия проверять короткими `assert` с понятным сообщением. Например, `assert features["listing_id"].is_unique, "Повторяются ID объявлений"`. `print()` помогает увидеть результат, `assert` останавливает расчёт, когда нарушена договорённость о данных.
- До расчёта признаков проверить уникальность `listing_id` в объявлениях и допустимые значения `is_deal` в разметке. После объединения проверить, что число объявлений сохранилось. Такие проверки уже стоят в `feature_engineering.ipynb` рядом с соответствующими операциями.
- Операцию, которая читается прямо в ячейке и встречается один раз, оставить в этой ячейке. Если одно и то же правило используется в нескольких местах, переиспользовать существующую функцию или выделить небольшую функцию с понятными входами и результатом. В проекте такой пример — `safe_divide()`.

## План любой правки

1. Найти ячейку, где формируется нужный столбец или файл. Посмотреть соседний код и выяснить, какие ячейки читают результат.
2. Внести изменение в месте расчёта. Для нетривиального решения добавить короткое пояснение причины.
3. Показать эффект на данных. Для очистки сверить размеры и пропуски, для объединения — ключи и число строк, для новой модели — метрики на тех же разбиениях.
4. Запустить затронутые ноутбуки сверху вниз в чистом ядре. Если изменились признаки, пересобрать зависящие от них таблицы и проверить итоговый CSV.
5. В описании правки указать, что изменилось, какие файлы пересобраны и чем проверен результат.
